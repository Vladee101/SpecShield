# SpecShield — модель угроз

**Версия 1.0 · для проверки безопасности**

Этот документ заявляет, что SpecShield защищает, от кого, где защита реализована
и где она заканчивается. Он написан, чтобы с ним спорили. Каждое утверждение либо
реализовано кодом, у которого есть тест, либо перечислено здесь как
нереализованное.

PRD §4 — источник по противникам и классам активов; этот документ добавляет точки
реализации и обоснования и фиксирует, где реализация расходится с проектными
документами.

---

## 1. Задача в одном абзаце

Инженеры хотят применять коммерческие LLM к проприетарному материалу. Ценность
материала частью в его **именах** — компания, клиенты, сервисы, модель данных, —
частью в его **семантике** — что делает код и как устроен бизнес. SpecShield
убирает первое и намеренно сохраняет второе, потому что двойник без семантики
бесполезен для модели. Эта сделка и есть весь продукт, и именно её проверяющий
должен первым делом решить, принимает он или нет.

## 2. Активы

| Актив | Где живёт | Последствие раскрытия |
|---|---|---|
| **A1** Проприетарные идентификаторы | Исходники, спецификации, схемы, имена файлов и каталогов | Атрибуция материала организации; конкурентная разведка |
| **A2** Соответствие псевдоним→имя | Хранилище (`.specshield/vault.bin`) | Обращает любой двойник, когда-либо созданный из этого проекта |
| **A3** Секреты | Исходники, конфигурация, фикстуры | Прямая компрометация работающей системы |
| **A4** Ключ проекта | Запечатан внутри хранилища | Псевдонимы становятся предсказуемыми; два двойника — связываемыми |
| **A5** Бизнес-семантика | Везде | Раскрытие того, как работает бизнес — **не защищается**, см. §6 |

A2 — актив с худшим радиусом поражения. Одно хранилище обращает каждый двойник,
который проект когда-либо произвёл, включая уже лежащие в логах провайдера
модели.

## 3. Противники

| # | Противник | Возможности | Статус |
|---|---|---|---|
| **T1** | Провайдер LLM, честный, но любопытный | Хранит промпты для обучения, разбора злоупотреблений или по запросу суда; сотрудники могут их читать | **Основной** |
| **T2** | Облачная синхронизация файлов | Молча выгружает хранилище или дерево проекта — OneDrive, Dropbox, Google Drive, iCloud | **Основной** |
| **T3** | История и синхронизация буфера обмена | Сохраняет или выгружает содержимое буфера, например Windows Cloud Clipboard | **Основной** |
| **T4** | Локальная вредоносная программа, украденное устройство | Читает файлы на диске от имени пользователя | **Частично** — только хранилище на диске |
| **T5** | Инсайдер с легитимным доступом | Читает настоящий проект напрямую | Вне охвата |
| **T6** | Целевой атакующий | Компрометация конечной точки, вычитывание памяти | Вне охвата |

T5 и T6 вне охвата, потому что SpecShield работает от имени пользователя и с его
файлами. Он не может защитить от того, у кого уже есть то, что он защищает.
Сказать об этом прямо полезнее, чем предложить меру, которая не сработает.

## 4. Границы доверия

```
┌─ машина пользователя ───────────────────────────────────────────────┐
│                                                                     │
│   файлы ──▶ разбор ──▶ псевдонимы ──▶ [ ШЛЮЗ ] ──▶ двойник ─────┐   │
│       ▲                       │                                 │   │
│       │                       ▼                                 │   │
│   патч ◀── восстановление ◀── хранилище (A2, A4)                │   │
│       ▲                                                         │   │
└───────┼─────────────────────────────────────────────────────────┼───┘
        │                                                         │
        │                  ══ граница доверия ══                  ▼
        │                                            буфер обмена / файл
        └──────────── ответ модели ◀────────── коммерческая LLM (T1)
```

**Ровно одна вещь пересекает границу наружу: двойник, прошедший шлюз экспорта.**
Всё остальное — оригиналы, хранилище, журнал аудита, контрольные суммы, индекс —
остаётся на машине. У приложения нет вообще никаких сетевых возможностей, поэтому
нет и пути в коде, которым можно было бы что-то отправить — намеренно или
случайно.

Внутрь ответ модели приходит как **недоверенный ввод**. Это строка, которая
переписывается лексически; она никогда не исполняется, никогда не разбирается как
конфигурация и никогда не может сама назвать идентичность (§5.6).

## 5. Защиты и где каждая реализована

### 5.1 Выдача псевдонимов — A1, A4

Псевдонимы — это выделяемые номера, `ORG_001`, `PRODUCT_001`, раздаваемые по
типам в порядке первой встречи и хранимые в хранилище (PRD §13, SDD §6.1). Они
несут **никакой информации об имени, которое заменяют**: ни хеша, ни длины, ни
категории сверх префикса типа, который двойнику нужен, чтобы читаться связно.

Это изменение относительно v1.1, где они выводились по HMAC от ключа проекта.
Причиной было согласие между машинами для общих хранилищ, которое PRD §15 теперь
выносит за пределы MVP; ценой был двойник, который никто не мог прочитать.
Проверяющему стоит отметить следствие: псевдонимы больше не воспроизводятся из
ключа, поэтому два хранилища над одним проектом разойдутся в том, какая компания
есть `ORG_001`.

Для проверяющего важны два свойства:

- **Устойчивость внутри хранилища.** Одна и та же идентичность всегда даёт один и
  тот же псевдоним, поэтому двойник воспроизводим, а восстановление однозначно.
  Перенумерация — явная операция (`specshield rekey`), а не побочный эффект.
- **Это последовательность, и она чего-то стоит.** Номер сообщает, сколько
  сущностей этого типа хранилище видело и в каком порядке они встретились. Это
  реальное раскрытие, которого схема на HMAC не допускала, и оно было принято в
  обмен на двойник, который человек может читать.

Идентичность — это `(scope_path, entity_type, real_name)`, никогда не одно имя.
Три несвязанных перечисления `Status` в трёх модулях — это три идентичности с
тремя псевдонимами. Схлопнуть их по имени было бы ошибкой корректности **и**
утечкой информации, поскольку раскрыло бы, что эти три связаны.

*Реализовано в* `crates/core/src/alias.rs`, `crates/core/src/sanitize.rs`.

### 5.2 Шлюз экспорта — A1

Прежде чем выпустить любой двойник, автомат Ахо — Корасик, построенный из **всех
идентифицирующих имён, которые знает хранилище**, плюс варианты регистра и
разделителей, сканирует двойник и **сообщает о каждом попадании**.

**Он не отказывает.** Читайте это прямо: двойник, содержащий известное хранилищу
имя, всё равно будет создан, и решать, отправлять ли его, — пользователю. Так
стало после того, как шлюз встретился с настоящим репозиторием, заблокировал 78
файлов из 107 по 124 различным именам — `Node`, `Screen`, `data` — и не записал
вообще ничего. Контроль, который не даёт продукту работать, не защищает никого,
потому что его отключают или продукт бросают. `--strict` возвращает отказ для
задачи CI, а `specshield verify` всегда был пофайловой формой того же.

**Секрет высокой уверенности по-прежнему отказывает, в обоих режимах.** Эта
асимметрия и есть весь замысел: утёкшее имя стоит конкуренту одной догадки,
утёкшие учётные данные немедленно пригодны любому, кто прочитает переписку, и
никакой перевыпуск их не отзовёт.

«Идентифицирующее» тоже стало у́же. Имя, состоящее из одного обычного слова, —
организация с названием `admin`, среда `staging` — не получает псевдонима и не
ищется (PRD §4.2), пока пользователь не назовёт его через `specshield term`.
Хранилище, знающее тип `Node`, раньше делало утечкой каждый `node_modules` в
lock-файле.

`_` и `-` считаются границами слова при этом сканировании, так что
`old_vantor_id` будет пойман. Шлюз работает на стороне Rust и в CLI, и в
настольном приложении.

Это самая важная защита, потому что она не зависит от правоты детектора. Если
обнаружение пропустило имя, шлюз ловит его в выводе. Полнота обнаружения —
метрика качества; шлюз — контроль безопасности.

**Одно его открывает: список разрешённых** (PRD FR-10). Имя, помеченное
пользователем как «никогда не заменять», исключается из сканирования. Эта дыра
обязана существовать — без неё разрешение имени, которое хранилище уже знает,
остановило бы его замену, оставило бы его в двойнике и затем блокировало бы
каждый экспорт навсегда без пути вперёд. Она ровно такой ширины, какую набрал
пользователь, и каждый вызывающий сообщает, сколько имён было исключено, так что
открытый шлюз никогда не молчит.

*Реализовано в* `crates/core/src/verify.rs`. *Тесты в*
`crates/cli/tests/error_matrix.rs`.

### 5.3 Затирание секретов — A3

С секретами работает механизм, намеренно отличный от механизма имён: они
**затираются односторонне** и никогда не восстанавливаются. Находка высокой
уверенности в двойнике — жёсткая блокировка. Обнаружение — набор регулярных
выражений плюс оценщик энтропии.

Секрет, прошедший туда и обратно, был бы секретом, который этот инструмент
услужливо занёс обратно в файл после отправки модели. Для затирания нет записи в
хранилище, и из `<<REDACTED:api_key>>` нет пути назад.

*Реализовано в* `crates/core/src/secrets.rs`.

### 5.4 Шифрование хранилища — A2, A4, T4

Поэлементный **AES-256-GCM** на каждой чувствительной колонке, а не шифрование
файла целиком. Ключ выводится **Argon2id** из парольной фразы пользователя; о
самой фразе не сохраняется ничего.

Каждый шифротекст привязан к своему месту через связанные данные
(`таблица:колонка:строка`), так что значение нельзя переставить между строками или
колонками даже тому, кто может писать в файл базы. Поиск по шифротексту даёт
**слепой индекс** — HMAC открытого текста под отдельным, доменно-разделённым
подключом, — он же делает ограничение уникальности из SDD §5 проверяемым без
расшифровки.

Ключевой материал обнуляется при освобождении.

> **Расхождение с проектными документами.** SDD §9.4 и §17.2 описывают SQLCipher
> и хранилище учётных данных ОС. Ни то, ни другое не построено. Шифрование файла
> целиком заменено поэлементным AEAD (решение D-9) после того, как встроенная
> сборка SQLCipher оказалась ненадёжной на трёх целевых платформах, а хранилище
> учётных данных не было реализовано вовсе: парольная фраза — единственный путь к
> ключу. См. §3.1 «Остаточного риска».

*Реализовано в* `crates/vault/src/crypto.rs`.

### 5.5 Контроль исходящего трафика — T1

- Набор возможностей Tauri **не** даёт ни сетевых, ни шелл-разрешений. Полный
  список — `core:default`, `core:window:allow-start-dragging`,
  `clipboard-manager:allow-write-text`. Тест утверждает, что список ровно такой,
  так что расширить его можно, только отредактировав тест и этот документ.
- Доступ к буферу обмена — **только на запись**. Читать буфер пользователя — не
  дело этого приложения.
- **У диалога выбора файла тоже нет разрешений.** `tauri-plugin-dialog`
  присутствует в `Cargo.toml`, но вебвью не выдано ни одно из его разрешений:
  диалог открывает Rust-команда, которая затем сама читает выбранный файл и
  возвращает содержимое. Выдать вебвью `fs:allow-read-*` было бы короче — и
  означало бы, что фронтенд может прочитать на машине что угодно. Как построено,
  единственный способ содержимому файла попасть в приложение — файл, который
  человек выбрал в нативном диалоге, и ни одна команда не принимает путь для
  чтения от вызывающего.
- CSP ограничена локальными ресурсами и источником IPC.
- Протокол ассетов отключён.
- Артефакты обновлений не собираются. Автообновление — сетевая зависимость в
  продукте, центральное утверждение которого в том, что сеть ему не нужна.
- CI гоняет весь набор тестов в сетевом пространстве имён без маршрута наружу,
  предварительно убедившись, что в этом пространстве действительно нет DNS: тест,
  который прошёл бы и при доступной сети, не доказывает ничего.

*Реализовано в* `app/src-tauri/capabilities/default.json`, `tauri.conf.json`,
`.github/workflows/ci.yml`.

### 5.6 Недоверенный вывод модели — входящее

Ответ модели переписывается лексически, а не разбирается. Три правила:

- Токен, похожий на псевдоним, но никогда хранилищем не выдававшийся, — это
  **неопознанный псевдоним**. Он остаётся дословно и блокирует применение патча.
  Ничего не угадывается, потому что угаданное имя — это неверный идентификатор,
  закоммиченный в настоящий репозиторий.
- Токен, совпавший только после нормализации, применяется, но **помечается как
  нечёткий** в сравнении — в том числе когда результат побайтно совпадает с
  оригиналом и никакого видимого изменения не даёт.
- Маркеры затирания остаются на месте.

*Реализовано в* `crates/core/src/restore.rs`, `crates/core/src/diff.rs`.

### 5.7 Обратная запись — целостность

Патчи сначала прогоняются вхолостую (`git apply --check`), прежде чем что-либо
будет тронуто, никогда не применяются к `main`, `master`, `develop` или `trunk` и
обратимы. Файл, чья контрольная сумма BLAKE3 изменилась с момента индексации,
блокирует применение патча наотрез: патч, собранный из устаревшего двойника,
может примениться *чисто* и молча откатить сделанные в промежутке правки, что
хуже, чем провалиться.

*Реализовано в* `crates/git/src/lib.rs`, `crates/index/src/lib.rs`.

### 5.8 Облачная синхронизация — T2

При создании и при открытии корень проекта и путь хранилища сверяются с
известными корнями синхронизации (OneDrive, Dropbox, Google Drive, iCloud).
Хранилище внутри такого корня выгружается третьей стороне, что противоречит
гарантии «только локально». Пользователя предупреждают; молча это никогда не
переопределяется.

*Реализовано в* `crates/vault/src/lib.rs` (`cloud_sync_root`).

### 5.9 Буфер обмена — T3

SpecShield никуда ничего не отправляет. Windows — отправляет: при включённых
истории буфера и синхронизации между устройствами ОС выгружает текст буфера в
учётную запись Microsoft **после** того, как шлюз отработал, — маршрут с машины,
которого шлюз не видит.

Поэтому полезная нагрузка несёт три зарегистрированных формата буфера обмена,
каждый со значением `DWORD 0`:

| Формат | Чем управляет |
|---|---|
| `ExcludeClipboardContentFromMonitorProcessing` | мониторами и логгерами буфера |
| `CanIncludeInClipboardHistory` | локальной историей Win+V |
| `CanUploadToCloudClipboard` | **синхронизацией между устройствами в учётную запись Microsoft** |

Третий и управляет выгрузкой; выставить только первые два — значит подавить
локальную историю и оставить синхронизацию работать. Буфер очищается по таймауту
и только если в нём всё ещё лежит собственная нагрузка SpecShield: безусловная
очистка уничтожила бы то, что пользователь скопировал с тех пор.

**Эти форматы рекомендательные, а не граница обеспечения.** Их соблюдают Windows
и корректно написанные менеджеры буфера. Менеджер, который их игнорирует, всё
равно захватит двойник. Двойник прошёл шлюз, так что это раскрытие обезличенного
содержимого, а не настоящих имён.

*Реализовано в* `app/src-tauri/src/clipboard.rs`.

### 5.10 Аудит — подотчётность

Локальный журнал «только на дозапись» фиксирует, что операция происходила: время,
операцию, количество файлов, количество сущностей, результат проверки,
назначение. Он не записывает **ни настоящего имени, ни содержимого** и
экспортируется в CSV. Он никогда не передаётся и отличается от телеметрии,
которой у этого продукта нет.

Поскольку ничего чувствительного в журнале нет, он переживает потерю ключа
хранилища и читается в режиме восстановления — ровно тогда, когда он и нужен
службе безопасности.

*Реализовано в* `crates/vault/src/lib.rs`. *Тест*:
`the_audit_log_never_carries_a_real_name`.

---

## 6. Что намеренно не защищается

SpecShield заменяет идентификаторы, сохраняя семантику. Следующее доходит до
модели по замыслу:

- **Бизнес-логика в прозе.** «`SERVICE_014` берёт комиссию 3% с выплат `ORG_007`
  клиентам из ЕС свыше 10 тыс. евро» раскрывает правило, юрисдикцию, размер
  комиссии и форму интеграции. Каждое имя в этом предложении заменено, а
  предложение всё равно и есть секрет.
- **Алгоритмы и подход к реализации.**
- **Форма архитектуры** — количество сервисов, связи между ними, мощность таблиц,
  структура эндпоинтов, топология модулей.
- **Комментарии и текст документации**, если пользователь их не удалит.
- **Структурное переопознание.** Характерной предметной модели плюс форм
  эндпоинтов часто достаточно, чтобы опознать организацию при всех заменённых
  именах.
- **Всё, что вставлено в модель руками**, вне инструмента.

## 7. Рассмотренные пути атаки

| # | Путь | Исход |
|---|---|---|
| P1 | Детектор пропускает имя, двойник экспортируется | **Сообщается, не блокируется.** Шлюз сканирует вывод независимо от обнаружения и называет каждое попадание; решает пользователь. `--strict` отказывает. |
| P2 | Имя встречается только внутри составного (`old_vantor_id`) | **Сообщается.** `_` и `-` — границы слова для шлюза. |
| P3 | Имя утекает через путь файла, а не содержимое | **Сообщается.** Пути двойника проходят тот же шлюз, что и содержимое. |
| P1b | Раскрывается имя из одного обычного слова | **Принято.** Организация `admin` или среда `staging` не заменяются и не ищутся, пока не названы, — PRD §4.2. Это намеренное сокращение охвата. |
| P1c | Раскрывается структура — имя сервиса, таблицы или колонки | **Принято, и это и есть продукт.** PRD §4.1: агент, который не может прочитать архитектуру, не может помочь её развивать. `specshield term` повышает любое структурное имя до идентичности. |
| P4 | Атакующий копирует файл хранилища | **Смягчено.** Каждая чувствительная колонка запечатана AEAD под ключом от Argon2id; сам файл даёт псевдонимы и счётчики, имён — нет. |
| P5 | Атакующий копирует хранилище и знает парольную фразу | **Не защищено.** Это равносильно обладанию проектом. |
| P6 | Модель возвращает токен, похожий на псевдоним, но выдуманный | **Заблокировано.** Неопознанный псевдоним; остаётся как есть; блокирует патч, пока человек его не назовёт. |
| P7 | Модель искажает токен (`SERVICE_H7K2QXImpl`) | **Применено и помечено.** Подстановка сообщается на проверку, даже когда ничего видимого не меняет. |
| P8 | Патч из устаревшего двойника молча откатывает правки коллеги | **Заблокировано.** Сверка контрольной суммы до любого патча. |
| P9 | Патч применяется прямо в `main`, минуя ревью | **Заблокировано.** Список защищённых веток, отказ наотрез. |
| P10 | Хранилище лежит в папке OneDrive и выгружается | **Предупреждение, не блокировка.** Пользователю сообщают; предлагается перенос. |
| P11 | Двойник попадает в облачный буфер Microsoft | **Смягчено рекомендательно.** Три формата буфера; несоблюдающий менеджер их обходит. |
| P12 | Секрет возвращается в файл после того, как его увидела модель | **Заблокировано.** Затирание одностороннее, записи в хранилище нет. |
| P13 | Приложение само вывозит данные | **Структурно невозможно.** Сетевых возможностей не выдано; CI доказывает, что набор проходит без маршрута наружу. |
| P14 | Две идентичности сталкиваются на одном псевдониме, восстановление становится неоднозначным | **Заблокировано.** Уникальный индекс по псевдониму плюс детерминированный разрешитель коллизий. |
| P15 | Повреждённое хранилище осматривают, и осмотр портит его ещё сильнее | **Заблокировано.** Режим восстановления открывает с `immutable=1` и не предоставляет методов записи; тест утверждает, что байты не изменились. |
| P16a | Имя внесено в список разрешённых и затем уезжает в двойнике | **Разрешено и сообщается.** FR-10 существует, чтобы пользователь мог решить, что обнаружение ошибочно. Количество исключённых имён показывается при каждом экспорте. |
| P16 | Режим восстановления используют, чтобы прочитать имена без парольной фразы | **Заблокировано.** Читаются только незапечатанные колонки; тест утверждает, что настоящее имя недостижимо. |
| P17 | Скомпрометированный или сломанный фронтенд читает произвольные файлы | **Заблокировано.** У вебвью нет файловых прав, а `pick_file` не принимает путь — он открывает диалог. Тест утверждает, что сигнатура такой и остаётся. |

## 8. Что проверяющему стоит проверить самому

Не верьте этому документу на слово ни в чём. Вот дешёвые проверки:

1. `cat app/src-tauri/capabilities/default.json` — вся поверхность разрешений,
   зафиксированная тестом `the_capability_set_stays_minimal`.
2. `grep -rn "reqwest\|hyper\|ureq\|curl" crates/ app/src-tauri/src/` —
   HTTP-клиента нет.
3. `cargo test --workspace` — 439 тестов, включая матрицу ошибок SDD §16.
4. `cargo run -p specshield-cli -- report corpus --strict` — метрики обнаружения
   на закоммиченном размеченном вручную корпусе.
5. Задача CI `offline` — набор проходит внутри сетевого пространства имён.
6. `specshield audit --csv` на любом проекте — что записывается, а что нет.
